# AutoTC

매뉴얼 TC(절차 + 기대결과)를 한 번 등록하면 PC 웹, 모바일 웹(MW), 안드로이드 앱에서 자동으로 실행하고, 결과를 QA 판정 방식(Pass / Fail / Flaky / Blocked / Skipped)과 결함 초안·이슈 목록으로 돌려주는 테스트 자동화 실행기입니다. 아이폰은 현재 사전 점검과 Maestro YAML 생성까지 지원합니다.

## 실행

1. [Node.js](https://nodejs.org) LTS(20 이상)를 설치합니다.
2. 프로젝트 폴더의 **`AutoTC.exe`** 를 더블클릭합니다.
   - 처음 실행하면 패키지와 테스트용 Chromium을 자동으로 설치합니다 (인터넷 필요, 수 분).
   - 브라우저가 열리고 콘솔(`http://127.0.0.1:4870`)이 나타납니다.
   - 검은 창을 닫으면 AutoTC가 종료됩니다.

`AutoTC.exe`가 없으면 `npm run build:exe`로 다시 만들 수 있습니다. Windows가 아니면 `npm start`로 실행합니다.

| 명령 | 설명 |
|---|---|
| `npm start` | 콘솔 실행 (exe와 같음) |
| `npm run ci -- --tags smoke` | 화면 없이 실행하고 종료 기준으로 성공/실패 판정 (아래 CI 참고) |
| `npm test` | 핵심 로직 단위 테스트 |
| `npm run build:exe` | `launcher/AutoTC.cs` → `AutoTC.exe` 빌드 (Windows 기본 csc.exe 사용) |

포트를 바꾸려면 환경변수 `AUTOTC_PORT`를 지정합니다. 콘솔은 이 PC(127.0.0.1)에서만 열립니다.

## 안드로이드 실행 준비

1. [Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools)를 설치하고 `adb`를 PATH에 추가합니다.
2. Java 17 이상과 [Maestro](https://maestro.mobile.dev)를 설치합니다. Windows는 zip을 풀고 `bin` 폴더를 PATH에 추가합니다.
3. 폰에서 개발자 옵션 → USB 디버깅을 켜고 PC에 연결한 뒤 "USB 디버깅 허용"을 승인합니다. 테스트 중에는 화면이 켜져 있고 잠금이 풀려 있어야 합니다.
4. `data/config.json`의 `android`를 채웁니다.
   - `appId`: 앱 패키지명 (예: `com.example.shop`)
   - `apkPath`: 실행 전에 설치할 APK 경로 (선택, 비우면 이미 설치된 앱 사용)
   - `serial`: 기기가 여러 대일 때 쓸 기기 (선택, `adb devices`의 첫 칸)
5. 요소 맵의 **안드로이드 id** 칸에 resource-id를 입력합니다. 앱 안에서 다른 화면으로 바로 가야 하는 `open` 스텝은 화면 표의 **안드로이드 딥링크**가 필요합니다.
6. 기기 관리 화면에서 모든 항목이 ✓인지 확인하고 실행 현황에서 안드로이드를 체크해 실행합니다.

동작 방식:
- TC마다 `launchApp(clearState)`로 앱 데이터를 초기화한 뒤 시작합니다. 입력 전에는 기존 값을 지웁니다(`eraseText`).
- 문구 확인(assertText)은 "요소 노출"과 "문구 일치" 두 명령으로 나눠, 요소가 없는지(스크립트·UI 문제) 문구가 다른지(제품 결함)를 구분합니다.
- 실행마다 logcat을 비우고 끝나면 저장합니다. 대상 앱의 `FATAL EXCEPTION`·ANR이 있으면 오류 유형 CRASH, 결함 심각도 Critical로 잡습니다.
- 식별자가 없는 요소를 쓰는 TC는 실행하지 않고 Blocked로 남깁니다. 요소 맵의 "개발팀 요청 목록"으로 요청하세요.
- 기기는 한 대에서 TC를 하나씩 실행합니다. TC 하나의 제한 시간은 `run.mobileTimeoutMs`(기본 5분)입니다.

## TC 가져오기 (엑셀 · 스프레드시트 · CSV)

TC 편집 → **TC 가져오기**에서 아래 중 하나로 불러옵니다. **양식 받기**로 예시와 작성 방법이 든 양식을 받을 수 있습니다.

| 자료 | 방법 |
|---|---|
| 엑셀 `.xlsx` | 파일 선택 |
| CSV / TSV | 파일 선택. UTF-8, 한국어 엑셀의 CSV(EUC-KR/CP949), UTF-16 모두 읽습니다 |
| Google 스프레드시트 | 링크 붙여넣기 → 불러오기. 시트 공유를 **링크가 있는 모든 사용자(뷰어)** 로 해야 합니다. 비공개 시트는 파일 → 다운로드 → Microsoft Excel(.xlsx)로 받아 파일로 올립니다 |

Google 스프레드시트는 xlsx로 내려받아 엑셀과 같은 규칙(병합 셀, 여러 시트)으로 읽고, 가져온 TC에는 원본 시트 링크가 남습니다. 시트를 고친 뒤에는 **다시 불러오기**를 누릅니다.

공통 규칙:

- **열 인식**: 머리글(TC ID/No, 테스트 항목/제목, 사전조건, 테스트 절차, 기대결과, 우선순위/중요도, 플랫폼/OS, 요구사항 ID, 대·중·소분류)을 자동으로 찾습니다. 위쪽 제목 행은 건너뛰고, "결과"·"비고" 열은 무시합니다. 잘못 잡힌 열은 화면에서 바꿉니다.
- **여러 행 TC**: ID 칸이 비었거나 병합된 행은 위 TC에 이어 붙입니다.
- **값 변환**: 우선순위 상/중/하·High/Low → P1/P2/P3, 플랫폼 PC/MW/AOS/iOS/공통 → 플랫폼 체크, 분류 열 → 태그. 쓸 수 없는 ID(한글 등)와 파일 안의 중복 ID는 `TC-IMP-001`처럼 새로 붙이고 원래 ID를 보관합니다.
- **스텝 변환**: 절차·기대결과 문장에서 요소 맵의 이름("비밀번호 입력창", "로그인 버튼")과 동작(진입·입력·클릭·선택·뒤로 가기 / 노출·미노출·문구·화면 이동)을 찾아 스텝으로 바꿉니다. 입력값과 확인 문구는 따옴표로 감싸야 합니다.
- **변환하지 못한 문장**이 하나라도 있거나 기대결과 확인 스텝이 없으면 그 TC는 **수동 유지**로 가져옵니다. 엑셀 원문은 TC 편집 화면에 함께 보이므로 스텝을 채우고 "적합"으로 바꾸면 자동화 대상이 됩니다. 문장을 추측해서 변환하지 않습니다.
- 같은 ID가 이미 있으면 기본으로 건너뛰고, "같은 ID는 덮어쓰기"를 켜면 덮어씁니다.
- `.xls`(옛 엑셀 형식)는 엑셀에서 `.xlsx`로 저장한 뒤 올립니다.

## TC 영역 매핑 (기획서 · 피그마 → 화면 · 영역)

**영역 매핑** 메뉴에서 기획서와 화면 디자인을 넣으면 TC마다 어느 화면의 어느 요소를 다루는지, 그 근거가 되는 기획서 문장은 무엇인지 찾습니다. 분석 방법은 세 가지이고, 결과의 검증·확신도·검토·반영은 모두 같습니다.

| 방법 | 비용 | 특징 |
|---|---|---|
| **규칙 기반** | 무료 | AI 없이 피그마 텍스트·버튼 레이어(레이어 이름으로 Button·Input·버튼 등을 찾음)와 텍스트 기획서(.txt/.md)의 키워드로 찾습니다. 피그마에서 가져온 화면에서만 위치를 찾고, 캡처 이미지·PDF는 읽지 못합니다 |
| **Claude Code** | 사용 중인 Claude 구독 안에서 | "요청 파일 만들기"를 누르면 나오는 문장을 Claude Code 대화창에 붙여넣습니다. Claude Code가 화면·기획서를 읽고 `response.json`을 쓰면 "응답 가져오기"로 들여옵니다. 캡처·PDF도 읽고 API 비용이 들지 않습니다 |
| **Claude API** | 유료 (platform.claude.com 크레딧) | 버튼 한 번으로 자동 분석합니다. API 키가 필요하고 실행 전에 호출 수와 대략 비용을 보여줍니다 |

1. **설정**: 피그마 개인 액세스 토큰(규칙 기반에 필요, 또는 `FIGMA_TOKEN`), Claude API 키(API 방식만, 또는 `ANTHROPIC_API_KEY`), 외부 AI 전송 동의(API 방식만). 키·토큰은 `data/state/ai.json`에만 저장되고 화면에는 가려서 보이며, 설정에서 삭제할 수 있습니다. 고객사 자료는 외부 AI 전송이 허용되는지 먼저 확인하세요 (Claude Code 방식도 자료가 Claude로 전송됩니다).
2. **자료**: 기획서(PDF·이미지·.txt/.md), 화면 디자인(프레임 PNG 캡처, 또는 피그마 링크 → 프레임 이미지와 텍스트 레이어를 가져옴). 에러·팝업 같은 상태 화면도 함께 넣어야 그 상태를 다루는 TC를 찾을 수 있습니다.
3. **TC 선택 → 분석 방법 선택**: 화면마다 UI 요소 목록을 만들고(TC 없는 영역 계산용), TC마다 화면·요소·영역·근거를 찾습니다. API 방식은 기획서·디자인을 첫 호출 뒤 캐시해 TC가 늘어도 자료 비용이 반복되지 않습니다. 스텝이 없는 수동 유지 TC는 엑셀 원문으로 분석합니다.
4. **검토**: 화면 위에 스텝 번호로 영역이 표시됩니다. 요소를 바꾸거나(기존 요소 또는 새 요소 이름) 승인·기획 문의·제외합니다.
5. **반영**: 승인한 결과만 반영합니다. 새 요소는 요소 맵에 식별자 미부여 상태로 추가되고(개발팀 요청 목록에 나타남), 근거의 정책 번호는 TC 요구사항 ID에, 매핑한 화면·요소는 TC에 기록됩니다.

AI가 지어낸 답을 걸러내는 규칙:
- **확신도는 규칙으로 계산**합니다. 높음: 화면·근거 있음, 요소 후보 1개 / 중간: 후보 2개, 근거나 화면 한쪽만, 영역을 못 찾은 문장, 디자인에 없는 상태 / 낮음: 후보 3개 이상, 문구가 디자인과 다름 / 근거 없음: 화면·근거 모두 없음(기획 누락 의심).
- **텍스트 기획서의 인용은 원문에서 직접 찾고, 없으면 버립니다.** PDF·이미지 기획서의 인용은 "원문 대조 불가"로 표시합니다.
- 피그마에서 가져온 화면은 기대결과의 따옴표 안 문구가 텍스트 레이어에 실제로 있는지 직접 대조합니다. 절차 문장의 따옴표(입력값)는 비교하지 않습니다.
- 자료에 없는 화면 id나 요소 맵에 없는 요소 이름을 답하면 버리고 "걸러낸 답변"으로 보여줍니다.
- 검토 화면 상단의 **"높음" 그대로 승인 비율**이 낮으면 AI 판단을 믿을 수 없다는 신호입니다.
- **TC 없는 영역**: 디자인의 버튼·입력창·링크·탭 중 어떤 TC의 영역과도 30% 이상 겹치지 않는 것. 화면 전체를 가리키는 영역(화면 진입)은 계산에서 뺍니다.

모델과 생각 깊이는 `data/config.json`의 `ai`(기본 `claude-opus-5-5`, `high`)에서 바꿉니다.

## TC 자동 작성 (기획서 · 화면 · 입력 조건표 → TC 초안)

**TC 자동 작성** 메뉴에서 TC를 두 단계로 만듭니다. 먼저 **테스트 조건**(무엇을 확인할지)을 뽑아 QA가 검토하고, 승인한 조건만 **TC 초안**으로 만든 뒤, 승인한 초안만 `data/tcs`에 저장합니다. 유료 API는 쓰지 않습니다.

| 방법 | 비용 | 하는 일 |
|---|---|---|
| **규칙 기반** | 무료 | **입력 조건표**(필드·요소·유형·필수·최소·최대·허용값·오류 문구)로 동등 분할·경계값(최소-1, 최소, 최대, 최대+1) 조건을 만들고, 바로 실행할 수 있는 TC와 데이터 행을 만듭니다. 텍스트 기획서에서는 "~시·~경우·~하면·이상·최대·필수" 같은 조건 문장과 "적절히·등·추후·협의" 같은 모호한 문장(기획 문의)을 찾습니다 |
| **Claude Code** | 사용 중인 Claude 구독 안에서 | 요청 파일(1단계 조건 / 2단계 초안)을 만들어 Claude Code 대화창에 맡깁니다. PDF·이미지 기획서와 화면도 읽고, 결정표·상태 전이·오류 추정 조건도 찾습니다. 2단계는 승인한 조건과 팀 TC 예시 2건을 함께 넘겨 형식을 맞춥니다 |

1. **① 자료·범위**: 기획서(텍스트는 `# 제목`으로 절을 나눠 범위를 고름), 화면(캡처·피그마), 입력 조건표(엑셀에서 복사해 붙여넣기 가능), 진입 방법(공통 흐름·화면)·제출 버튼·오류 문구 요소·성공 확인, TC ID 접두어. 한 번에 한 기능씩 범위를 좁혀야 결과가 정확합니다.
2. **② 테스트 조건**: 조건마다 기법(동등 분할·경계값·결정표·상태 전이·오류 추정·유스케이스), 유형(정상·예외·경계·권한·오류 처리), 우선순위, 근거 인용을 보여줍니다. 고치거나 승인·기획 문의·제외합니다. 옆에 **기획 문의 목록**(복사해서 기획자에게 전달)과 **정책 번호별 조건 수**, 기법·유형 분포가 나옵니다. 조건을 다시 뽑아도 검토한 결과는 유지됩니다.
3. **③ TC 초안**: 초안마다 배지로 검토할 곳을 보여줍니다 — 실행 가능 / 식별자 필요 / 스텝 오류 / 스텝 직접 작성, 근거(원문 확인·대조 불가·조건표·없음), 새 요소, **약한 기대결과**("정상 동작"처럼 막연하거나 확인 스텝 없음), **중복 의심**(기존 TC·다른 초안과 제목 유사도 80% 이상), 가정.
4. **④ 반영**: 승인한 초안만 `접두어+번호`로 저장합니다. 태그 `generated`와 출처(프로젝트·초안·방법·기법·조건·승인 시각)를 TC에 남기고, 근거의 정책 번호는 요구사항 ID가 됩니다. 새 요소는 식별자 없이 요소 맵에 추가되고, 스텝이 없는 초안은 "수동 유지"로 저장됩니다.

AI 답을 그대로 믿지 않는 규칙:
- **인용은 원문과 대조**합니다. 텍스트 기획서에서 찾을 수 없는 인용은 버리고, 근거가 남지 않은 조건은 "기획서 근거를 찾지 못했습니다 (AI 추정)"으로 표시합니다.
- **스텝은 TC 검증 규칙으로 검사**합니다. 요소 맵에 없는 요소·없는 액션이 있으면 구조화 스텝을 버리고 자연어 절차에서 다시 변환하며(TC 가져오기와 같은 변환기), 그래도 안 되면 원문만 남깁니다.
- 승인하지 않은 조건 번호, 형식이 틀린 새 요소 이름은 뺍니다. 확신도 같은 AI 자기평가는 받지 않습니다.
- 방법별 **채택률**(승인 ÷ 초안)을 보여줍니다. 낮으면 범위·조건표·예시를 손볼 신호입니다.

예시 자료: `examples/tc-generate/`의 결제 정보 입력 기획서와 조건표로 saucedemo 결제 정보 화면 TC(정상 제출 1건 + 필수 오류 데이터 행 3개)를 만들어 바로 실행할 수 있습니다 (진입: `flow.login` + `screen.checkoutInfo`, 제출 `checkout.continue`, 오류 `checkout.error`, 성공 확인: 주소 포함 `checkout-step-two`).

## CI (GitHub Actions)

`.github/workflows/autotc.yml`이 GitHub에 올라가면 자동으로 동작합니다.

| 언제 | 무엇을 |
|---|---|
| `main` 푸시, PR | 단위 테스트 · 비밀값 평문 검사 (예시 사이트 saucedemo는 자동으로 돌리지 않음) |
| Actions 탭에서 수동 실행 | 단위 테스트 후 태그·플랫폼을 지정해 자동화 실행 |

실제 대상 사이트로 바꾼 뒤 푸시·야간 자동 실행이 필요하면 워크플로 `e2e` 작업의 `if:` 조건을 지우고 `schedule`을 추가합니다.

- 종료 기준(`data/config.json`의 `exitCriteria`)을 못 맞추면 워크플로가 실패로 표시됩니다.
- 실행 요약이 Actions 실행 화면에 표로 나오고, `summary.md`, `junit.xml`, 스크린샷·영상·트레이스, Playwright HTML 리포트를 아티팩트로 14일간 보관합니다.
- 결함을 일부러 심은 예시 TC(`demo-bug` 태그)와 화면 비교 TC(`visual` 태그, 리눅스 기준 이미지가 아직 없음)는 CI에서 제외합니다. 리눅스 기준 이미지를 `--update-baselines`로 만들어 커밋하면 `visual`도 켤 수 있습니다.
- 수동 실행에서 로그인 TC는 저장소 Secrets의 `SAUCE_PASSWORD`가 있어야 실행됩니다 (없으면 Blocked → 종료 기준 미충족).
- 슬랙 알림: 저장소 Settings → Secrets에 `AUTOTC_SLACK_WEBHOOK`(수신 웹훅 URL)을 넣으면 실행마다 결과를 보냅니다.
- CI의 이슈·이력은 실행마다 새로 시작합니다. 이슈를 이어서 관리하는 것은 로컬 콘솔에서 합니다.

명령줄 옵션:

```
npm run ci -- --platforms pc,mw,api --tags smoke --exclude-tags demo-bug --label "스모크" --out report
  --tc TC-LOGIN-001,TC-CART-001   지정한 TC만
  --update-baselines              화면 비교 기준 이미지를 이번 화면으로 갱신
  --no-gate                       종료 기준을 못 맞춰도 성공 처리 (리포트만 필요할 때)
종료 코드: 0 충족 · 1 미충족 · 2 실행 오류
```

## 판정과 분류 규칙

- **Flaky**: 첫 시도 실패, 자동 재시도 통과. 최근 10회 중 3회 이상 Flaky면 격리되어 통과율에서 빠집니다.
- **Blocked**: 사전 점검 실패(URL 접속 불가, 브라우저·기기 없음 등), 비밀값 없음, 스크립트 변환 실패. 통과율에서 빠지고 종료 기준에서 따로 셉니다.
- **데이터 행**: 행 중 하나라도 실패하면 TC는 Fail, 증적·실패 스텝은 가장 나쁜 행 기준입니다.
- **실패 분류 제안**: 값이 다름(응답 코드·응답 값·스키마 포함) → 제품 결함 의심 / 접근성 위반 → 제품 결함 의심 / 화면 비교 차이 → 제품 결함 또는 UI 변경 / 요소 없음 + 다른 플랫폼에선 같은 스텝 통과 → 스크립트 수정 필요 / 요소 없음 + 모든 플랫폼 실패 → 제품 결함 또는 UI 변경 / 네트워크·타임아웃·비밀값 없음 → 환경 문제. 확정은 QA가 결과 상세 화면에서 합니다.
- **이슈**: `플랫폼 | TC | 스텝 | 오류 유형 | 대상`이 같으면 같은 이슈로 묶고 발생 횟수만 올립니다. 수정 완료 후 재검증이 Pass면 종료, 다시 실패하면 재오픈됩니다.
